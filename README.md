# dsh-plugin-ide-open

Плагин DeepSeek Harness: клик по файлу в Web UI открывает файл в **IntelliJ IDEA**,
а не во встроенном правом сайтбаре.

```
обычный клик по файлу      → IntelliJ IDEA (с переходом на строку, если ссылка её знает)
Ctrl / Cmd / Alt + клик    → прежний просмотр в сайтбаре DSH
план, чат субагента, навык → сайтбар DSH, как раньше
IDEA не найдена / отказ    → клик ведёт себя ровно как до установки плагина
```

## Что делает

- Обычный клик по ссылке на файл — в сообщении ассистента, в строке `read`, в карточке
  результата, в дереве файлов, в изменениях — открывает этот файл в IDEA.
- Если ссылка указывает строку (`read` с `offset`, `файл:42` в Markdown), IDEA
  открывает файл сразу на этой строке (`--line`).
- Ctrl/Cmd/Alt+клик оставляет файл в сайтбаре (ровно один клик — следующий
  обычный клик снова уходит в IDE): превью Markdown, диффы и всё остальное
  никуда не девается.
- Всё, что не является файлом (`dsh-resource://plan/…`, чаты субагентов,
  навыки), открывается в сайтбаре как обычно.
- Если лаунчер IDEA не найден или запуск не удался, клик **не проглатывается**:
  плагин отдаёт навигацию сайтбару, то есть ведёт себя как до установки.

## Как это работает

В DSH нет настройки «внешний редактор». Каждая файловая ссылка в Web UI в итоге
вызывает `ctx.sidebarRight.openResource()` (или его session-scoped sibling
`openResourceIn()`), а тот раскрывает правую колонку. Поэтому плагин состоит из
двух половин:

| Половина | Файл | Роль |
|---|---|---|
| Host (`node`) | [`index.js`](index.js) | Два маршрута на `webServer`: `GET /ide-open/status` и `POST /ide-open/open`. Находит лаунчер IDE, проверяет путь, запускает процесс. |
| Browser | [`client.js`](client.js) | Подменяет `openResource`/`openResourceIn`: файловые адреса уходят на host, остальные — в сайтбар. |

Почему именно так:

- **Отдельный host-маршрут, а не существующий «Open In…».** В DSH уже есть меню
  «Open In…» (`dsh-host-open-in-app`) с IntelliJ IDEA в каталоге, но его маршрут
  запуска открывает **только каталог** (`stat(path).isDirectory()`), а каталог
  приложений фиксирован на этапе сборки и не расширяется плагином.
  `session.openWorkspacePath({ application })` тоже не подходит: он жёстко
  проверяет, что приложение зарегистрировано в ОС как обработчик **этого** типа
  файла, поэтому для произвольного файла IDEA он откажет.
- **`webServer.register` + `connection.requestRejection`.** Тот же приём, что в
  штатном `dsh-host-open-in-app`: маршрут закрыт Host/Origin-проверкой и
  аутентификацией браузерной сессии, тело ограничено 64 КиБ.
- **Никаких зависимостей.** Пакет не тянет ни одного npm-пакета и не требует
  сборки: клиентская половина — обычный script, который регистрирует фабрику в
  `window.__ModuleLoader__` (ровно тот формат, что отдаёт сборщик DSH).
- **Ни одного обязательного `inject`.** Плагин с недоступным сервисом остаётся
  `pending`, а boot-аудит Web-клиента считает `pending` провалом всего boot.
  Поэтому `sidebarRight` ожидается во вложенной области (`ctx.inject([...])`):
  при выключенном сайтбаре плагин становится инертным, а UI грузится.

## Установка

Пакет объявляет `dsh.bundle`, поэтому он ставится и управляется как бандл — через
страницу **Plugins** в Web UI или командой.

**Приложение DeepSeek Harness (Electron) использует профиль `desktop`:**

```sh
dsh plugin --profile desktop add git+https://github.com/Shiccah/dsh-plugin-ide-open.git
```

**`dsh web` использует профиль `web`:**

```sh
dsh plugin --profile web add git+https://github.com/Shiccah/dsh-plugin-ide-open.git
```

Локально, из клона:

```sh
git clone git@github.com:Shiccah/dsh-plugin-ide-open.git
dsh plugin --profile desktop add "$PWD/dsh-plugin-ide-open"
```

После установки **перезапустите приложение** (профиль `desktop` не подхватывает
новый слой на лету). Профиль `web` с `patchReload: live` монтирует запись в уже
запущенный процесс.

Проверить, что запись попала в композицию:

```sh
dsh --profile desktop --dump-config | grep -A 3 "id: ide-open"
```

> `--dump-config` перезаписывает `cordis.yml` в каталоге профиля — это дамп для
> чтения, а не источник загрузки; композиция собирается из `dsh.profile.bundles`
> в `package.json` и `cordis.patch.yml`.

Ручную запись добавлять не нужно: патч бандла
([`cordis.patch.yml`](cordis.patch.yml)) сам вставляет строку. Отключить плагин,
не удаляя пакет, можно на странице **Plugins**.

## Конфигурация

Настройки читает только host-половина: браузерная половина создаётся Web-boot'ом
без конфига и узнаёт решение хоста из `GET /ide-open/status`.

| Поле | По умолчанию | Значение |
|---|---|---|
| `app` | `intellij` | Продукт JetBrains для автопоиска: `intellij`, `pycharm`, `webstorm`, `phpstorm`, `goland`, `rider`, `clion`, `datagrip`, `rustrover`, `androidstudio`. |
| `command` | — | Явный лаунчер вместо автопоиска: путь, имя в `PATH` или `[команда, ...фиксированные аргументы]`. |
| `args` | `[['--line','{line}'], ['--column','{column}'], '{path}']` | Шаблон аргументов. Группа (вложенный список) исчезает целиком, если в ней есть незаполненный плейсхолдер, — поэтому неизвестная строка не оставляет висящий `--line`. |
| `launchWatchMs` | `1000` | Сколько миллисекунд ждать быстрого падения запуска, прежде чем считать его успешным. |

Свои настройки кладутся в патч-слой профиля (`~/.dsh/profiles/<профиль>/cordis.patch.yml`).
Запись с тем же `id` **переопределяет** конфиг уже вставленной строки, а не
монтирует плагин второй раз; поле `name` — проверка, что правится именно эта
строка (при несовпадении патч пропускается с предупреждением):

```yaml
- id: ide-open
  name: "dsh-plugin-ide-open"
  config:
    app: intellij
    # Явный лаунчер, например для Toolbox-скрипта:
    # command: "/Users/me/Library/Application Support/JetBrains/Toolbox/scripts/idea"
    # Другое поведение аргументов, например VS Code:
    # command: code
    # args:
    #   - ["-g", "{path}:{line}"]
    #   - "{path}"
```

Автопоиск лаунчера, если `command` не задан:

- **macOS** — `IntelliJ IDEA.app` (и варианты Ultimate/CE/Community) в
  `/Applications` и `~/Applications` → скрипт Toolbox
  `~/Library/Application Support/JetBrains/Toolbox/scripts/idea` → `/usr/local/bin`
  и `/opt/homebrew/bin` → `PATH`.
- **Windows** — каталоги продукта под `%ProgramFiles%\JetBrains` и
  `%LOCALAPPDATA%\Programs` (свежая версия первой) → `PATH` (`.exe` по `PATHEXT`).
- **Linux** — скрипт Toolbox → `PATH` → `snap` → `flatpak`.

Окружение запуска очищается по правилу самого DSH (`KEY|PASSWORD|SECRET|TOKEN` и
все `DSH_*`): IDE хранит своё окружение для терминалов, поэтому без очистки
API-ключи хоста уехали бы в каждую оболочку, открытую в редакторе. `PATH`, `HOME`,
локаль и прокси сохраняются.

## Проверка

```sh
node --test test/*.test.js
```

Юнит-тесты покрывают разбор адреса, шаблон аргументов, валидацию тела запроса,
определение лаунчера и классификацию запуска (включая реальный `spawn`), а также
перехват навигации в браузерной половине на фейковом контексте.

Проверить, что лаунчер находится на этой машине, ничего не запуская:

```sh
node -e "import('./index.js').then(async m => console.log(await m.createLauncherCache(m.resolveOptions()).status()))"
```

Диагностика в браузере: DevTools → Network — при клике по файлу должен быть
`POST ide-open/open`; при неудаче в консоли будет строка
`ide-open: could not open … in the IDE`. Host пишет
`ide-open: serving /ide-open/status and /ide-open/open for "intellij"` при загрузке.

## Как это ломается и что делать

Плагин опирается на внутренние точки DSH, поэтому сломаться может предсказуемо:

| Симптом | Причина | Правка |
|---|---|---|
| В консоли `ide-open: could not read the host launcher status` | Маршрут `/ide-open/*` не зарегистрирован: нет `webServer`/`connection` или host-половина не загрузилась | Проверить лог загрузки и `--dump-config` |
| Клик всегда открывает сайтбар, ошибок нет | Host ответил `available: false` — лаунчер не найден | Задать `command` в конфиге |
| Строка «IDE не найдена» | `config.app` указывает на продукт, которого нет | Сменить `app` или задать `command` |
| Файл открывается, но не на нужной строке | Лаунчер не поддерживает `--line` | Переопределить `args` |
| Плагин вообще не появился в композиции | Не перезапустили приложение либо пакет не объявляет `dsh.bundle` | Перезапустить, проверить `--dump-config` |
| В boot-аудите `pending (waiting for service…)` | Плагин объявил обязательный `inject` — так делать нельзя | Сообщить об ошибке: обязательных `inject` быть не должно |

## Известные ограничения

- **Доступность читается один раз за загрузку страницы.** IDEA, установленная при
  открытом UI, подхватится после перезагрузки страницы (и перезапуска host).
- **Плагин не расширяет меню «Open In…»** и не меняет системные ассоциации файлов.
- **Правки конфига требуют перезапуска** для профиля `desktop`; `web` подхватывает
  live.
- **Только JetBrains-семейство из коробки.** Другие редакторы выражаются через
  `command` + `args`; для VS Code нужен `-g {path}:{line}`, для сложных случаев —
  свой скрипт-обёртка.
- **Позиция по колонке** передаётся только если её знает вызывающая сторона; DSH
  сейчас передаёт только строку.

## Разработка

Проверено на DSH 0.2.1-alpha.1 в изолированном профиле с реальным браузером:
пакет попадает в `dsh.client`-граф как `dsh-plugin-ide-open/client.js`, строка
монтируется без ошибок активации, `GET /ide-open/status` отвечает найденным
лаунчером, `apply` клиентской половины выполняется и запрашивает статус у хоста.
Формат бандла сверен с DSH 0.2.0-rc.2 (сборка внутри приложения), а `application`
запуска сверен с родительским `spawn` в живом процессе.

```
index.js            host-половина (cordis-плагин: name/inject/apply + экспорт чистых функций)
client.js           браузерная половина (классический script, регистрация в __ModuleLoader__)
cordis.patch.yml    патч бандла: вставляет строку плагина в композицию профиля
index.d.ts          типы конфига и публичных функций
test/               node --test
```

Сборка не нужна: `client.js` — это ровно тот формат, который загружает система
модулей клиента. Требования к нему: `id` равен имени пакета, фабрика возвращает
объект с `apply`, никаких top-level `import`/`export`, из `require()` доступны
только платформенные модули (`react`, `@deepseek-ai/cordis`,
`@deepseek-ai/dsh-client-store`, `-ui-slots`, `-ui-primitives`, `-ui-dockkit`) —
этот плагин не использует ни одного.

Причина, по которой в репозитории нет ветки про `ctx.connection.rpc`: RPC-канал
(`rpc.handle`/`rpc.call`) — рабочая альтернатива маршрутам и дал бы меньше кода за
счёт готовой аутентификации, но выбранный вариант повторяет штатный
`dsh-host-open-in-app`, то есть тот путь, который сопровождающие DSH тестируют
именно для запуска локальных приложений.
